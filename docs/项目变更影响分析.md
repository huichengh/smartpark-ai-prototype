# 项目变更影响分析（提示词 08）

> 实施日期：2026-11-01　｜　对应提交：见 git log
> 定位：在**不改动正式计划**的前提下，推演"审批延误 / 停工 / 资源冲突 / 设计变更"对工期、
> 关键路径、里程碑与成本的影响；要落地必须走变更申请 + 人工审批。

---

## 一、边界先说清楚

| 问题 | 本模块的回答 |
|---|---|
| 会直接改计划吗？ | **不会**。模拟只读，结果里带 `baseline_untouched: true` |
| 怎么才落地？ | 提交变更申请（`PENDING`）→ 有 `project:APPROVE` 的人审批 → 才更新计划完工日与预算 |
| 会不会给"延期概率"？ | **不会**。没有带标签的历史延期样本，任何概率都是编的；只给确定的天数与成本 |
| 前端传的数字算数吗？ | 不算。创建变更申请时**服务端重新推演**，不采信前端天数与金额 |

## 二、做了什么

### 新增接口（2 个）

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| POST | `/projects/{id}/change-impact` | `project:VIEW` | 只读推演，返回工期/关键路径/受影响任务/里程碑/成本 |
| POST | `/projects/{id}/change-requests` | `project:ADD` | 固化为变更申请（PENDING），服务端重算 |

审批复用已有的 `POST /projects/{id}/changes/{change_id}/decision`
（已实现：审批通过后顺延 `planned_end_date` 并增加 `budget`，写审计）。

### 引擎（纯函数）

`app/services/change_impact_engine.py`：

- `simulate(tasks, edges, scenarios, daily_cost, milestones)` — 叠加顺延后重算两遍 CPM，输出差异
- 校验：空 WBS、无情景、任务不存在、负顺延、超 365 天、未知类型、负日成本 —— **一律拒算**
- 受影响任务区分类型：`FINISH_SHIFT`（工期顺延）/ `FLOAT_GAINED`（只是时差变大）/
  `BECAME_CRITICAL`（时差被吃满转关键）

> 为什么要分类：把"时差变大"和"工期顺延"混在一张表里，读者会以为每条都要加人加钱。

### 共用一份 CPM

把原 `compute_critical_path` 里的前推/后推抽成 `compute_cpm(nodes, edges)`，
甘特图与变更模拟**共用同一实现**；项目网络加载也抽成 `build_network()`。
这样"同一个计划不会算出两个工期"——项目此前吃过"合同到期四份实现、37/39 两个值"的亏。

## 三、两个实现中修正的判断

1. **已完成里程碑不顺移**。第一版把所有里程碑整体后移，导致"立项批复（已达成，2026-08-08）"
   被推定为 08-18。已达成是既成事实，改动它等于篡改历史。现在按状态过滤，
   并在返回里带 `achieved: true`。
2. **"受影响"不等于"要加资源"**。第一版把时差变化也写成"受影响任务"，
   测试用例通过但语义误导。已加 `change_kind` 区分，并按"是否真的顺延"排序。

## 四、验证

```bash
cd backend
python check_change_impact.py   # 30 条金标准（纯函数，不需要服务）
```

金标准里有一个可手算的网络：`A(3)→B(4)→D(2)`、`A(3)→C(2)→D(2)`

| 用例 | 期望 | 实测 |
|---|---|---|
| 基准工期 | 9 天 | ✔ |
| 关键任务 | A、B、D | ✔ |
| C 的总时差 | 2 天 | ✔ |
| B 顺延 3 天 | 工期 12 天 | ✔ |
| C 顺延 2 天（未超时差） | 工期不变，C 转关键 | ✔ |
| C 顺延 3 天（超 1 天） | 工期 +1 | ✔ |
| 日成本 1200 × 顺延 4 天 | 4,800 元 | ✔ |
| 未提供日成本 | 不出成本数字 | ✔ |

接口实测（项目 1，关键任务顺延 10 天、日成本 5000）：

```
基准工期 294 天 → 调整后 304 天（+10）
成本影响 50,000 元
已达成里程碑：立项批复 / 方案评审 / 开工 —— 顺移 0 天
未完成里程碑：主体完成 —— 推定 2027-01-16（+10 天）
```

闭环实测：`admin` 提交 `CHG01003` → `p1_manager` 审批通过 →
`planned_end_date` 2027-05-19 → **2027-05-29**，`budget` +50,000，审计日志留痕。

回归：`smoke 92/0`、`check_fields 139 路径 0 问题`、`check_permissions 0/0`、
`check_tools 25/0`、`check_intent 50/50`、`check_operating 33/33`、`qa_suite 47/0`。

## 五、前端

项目详情页新增「变更影响分析」标签：

- 选任务（默认选中第一条**关键**任务——非关键任务的顺延常被时差吃掉，会让人误以为推演没生效）
- 选变更类型、填顺延天数与日成本（日成本可留空，留空就不出成本数字）
- 结果：工期 KPI（基准/调整/顺延/成本）→ 受影响任务表（带影响类型）→ 里程碑表 →
  风险因素模板 → 口径声明 + 「提交变更申请」

## 六、明确没做的

| 事项 | 原因 |
|---|---|
| 资源冲突的**自动识别** | 需要资源日历与人员技能矩阵，当前数据模型没有；现在由使用者指定顺延天数 |
| 历史项目风险模型 / 延期概率 | 没有带标签的历史延期样本，做了就是伪科学（提示词明确禁止） |
| 多情景组合寻优（哪个组合最省） | 属运筹优化，需要先有资源约束与成本函数 |
| 变更对 SPI/CPI 的联动重算 | EVM 依赖实际完成量，推演阶段没有；只在结果里给工期偏差率，不伪造指数 |
| 搭接关系（SS/FF 之外的部分开始-完成） | 当前按 FS 逻辑推里程碑顺移，已标注"需项目人员确认" |
