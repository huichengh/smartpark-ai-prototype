## 0. 测试策略：先看"没有测什么"

既有校验脚本（`smoke_test` 92 项、`check_fields`、`check_routes`、`check_permissions`、
`check_tools` 23 项、`check_intent` 41 项）**全绿**。它们都在验"正常路径能不能走通"，
所以我一开始就没有再跑它们，而是问了一个不同的问题：

> **哪些事是这套检查结构上测不到的？**

两条：

1. **换个身份去打**。所有脚本都用 `admin` 或固定的少数身份，从没试过"企业管理员去读别人的数据"。
   数据范围缺陷只有在**换身份**时才会显形。
2. **传坏参数 / 试探边界**。冒烟测试只发合法请求。

于是新增对抗性测试套件 `backend/qa_suite.py`（5 个分组、53 项），并刻意遵守两条纪律：

- **用例先写"应有行为"，不看现状**——先让测试失败，再判断是代码错了还是测试错了；
- **不许有"空断言"**：早期版本里我把断言写在 `if items 非空:` 里面，结果列表为空时断言被静默跳过，
  测试变成"永远通过"。这条纪律当场就救回了两个新增的越权用例（见缺陷 2）。

**结果**：53 项中最终 47 通过、1 警告、5 提示、0 失败。

## 缺陷 1（P0 · 数据越权）企业管理员能看全园区的数据

### 现象

用企业管理员 `tenant1` 登录后：

| 接口 | 企业管理员实际可见 | 应当可见 |
|---|---|---|
| 企业列表 | **128 家**（全库 344） | 1 家（自己） |
| 账单 | **13,248 条** | 124 条 |
| 合同 | **95 份** | 1 份 |
| 工单 | **589 条**（其中多数属别家企业，含报修人手机号） | 0 条 |
| 会议室预定 | **177 条** | 0 条 |

还可以直接读别家企业的完整档案：`GET /enterprise/enterprises/2` → **200**，
返回统一社会信用代码、注册资本、法人、联系人邮箱。

### 排查过程（先说结论：不是守卫写错了）

第一反应是"企业详情没做归属校验"。打开代码一看，**守卫写得完全正确**：

```python
# app/api/v1/enterprise.py 详情接口
if auth.enterprise_id and auth.enterprise_id != ent_id:
    raise HTTPException(403, "企业账号只能查看本企业档案")
```

问题在左边那个变量：`auth.enterprise_id` **永远是 `None`**。

顺着查数据库：

```
tenant1: id=28, park_id=1, enterprise_id=NULL, 角色=ENTERPRISE_ADMIN(data_scope=ENTERPRISE)
```

再回到播种代码，`seed_users()` 建 `User` 时用了一长串参数，
**从头到尾没写 `enterprise_id`**。全库唯一的 ENTERPRISE 范围账号没有被绑定到任何企业。

### 根因

> **一个字段没赋值，把四处守卫同时变成空操作。**

`contract.py`、`enterprise.py`、`finance.py` 里一共 7 处
`if auth.enterprise_id:` 形式的守卫，全部因为该字段为 `NULL` 而静默跳过；
过滤器退化成上一层的园区范围，于是企业管理员拿到了"整个园区"的可见域。

这和本项目历史上吃过的亏是**同一类**：
守卫没有抛错、没有日志、页面看起来一切正常——**静默失效比报错危险得多**。

### 修复

1. **补数据**：`seed_data.py` 新增 `seed_enterprise_bindings()`，
   把 ENTERPRISE 范围账号绑定到其所在园区企业编号最小的那家（确定性，可复现）。
2. **改成 fail-closed**：`AuthContext` 新增 `visible_enterprise_ids()`，
   当范围是 ENTERPRISE 却**没有归属企业**时返回**空列表**（什么都看不到），而不是 `None`（看到全部）：

   ```python
   if self.data_scope in ("GROUP", "PARK", "DEPARTMENT", "PROJECT"):
       return None
   if self.user.enterprise_id:
       return [self.user.enterprise_id]
   return []          # ← 算不出范围时宁可少给，也不能多给
   ```

   并把 7 处 `if auth.enterprise_id:` 统一换成 `auth.enterprise_scope_clause(...)` /
   `auth.require_enterprise(...)`。这样即便将来又漏了绑定，账号会"看不到数据"——
   明显、会立刻被发现，而不是静默越权。
3. **补上两处从未做过过滤的模块**：工单（`work_orders`）与会议室预定
   （`meeting_room_bookings`）都带 `enterprise_id`，但列表接口根本没查过这个字段。
   修完后两者对 `tenant1` 均正确显示 0 条。

### 回归结果

`tenant1` 现在：企业列表 1 家、合同 1 份、账单 124 条、工单 0 条、会议室预定 0 条；
读别家企业详情/合同/账单 → 403。园区负责人跨园区访问仍为 403（未受影响）。

## 缺陷 2（P1 · 数据不一致）"90 天内到期合同"有两个数

### 现象

同一指标在三个地方显示不同的值：

| 位置 | 显示 |
|---|---|
| 驾驶舱 KPI「90天内合同到期」 | **37** |
| 合同管理页「90 天内到期」 | **39** |
| `/contracts/expiring?days=90` | **37** |

### 排查

直接查库，按状态分组统计 `0 <= days_left <= 90` 的合同：

```
EXPIRING     37
TERMINATED    2      ← 差额就在这里
```

两处实现的差别是**状态过滤**：

- `/contracts/expiring` 用 `status in ("ACTIVE","EXPIRING")` → 正确排除已终止合同 → 37
- `/contracts` 的 `stats.expiring_90` 只比日期、不看状态 → 多算 2 份已终止合同 → 39

继续搜全仓库，发现这个指标**一共四份实现**，其中两份漏了状态判断：

| 位置 | 状态过滤 | 结果 |
|---|---|---|
| `dashboard_service` 驾驶舱 KPI | ✔ | 37 |
| `api/v1/enterprise.py` 一企一档 | ✔ | 37 |
| `api/v1/contract.py` `stats.expiring_90` | ✘ | **39** |
| `dashboard_service` `contract_expiring` 字段 | ✘ | **39** |

### 业务判断

**已终止的合同不可能续租**，把它算进"到期预警"会凭空多出催办任务；
而"多算"比"少算"更难被发现——没人会去质疑一个看起来合理的数字。

### 修复

按项目既有的 engine 模式新建 `app/services/contract_engine.py` 作为**唯一口径**：

```python
EXPIRING_WINDOW_STATUSES = ("ACTIVE", "EXPIRING")

def is_expiring_within(status, days_left, window) -> bool:
    if status not in EXPIRING_WINDOW_STATUSES or days_left is None:
        return False
    return 0 <= days_left <= window
```

四处实现全部改为调用它；另外 `/contracts?expiring_days=90` 这个**过滤参数本身**此前也没排除
已终止合同（列表因此返回 39 条），一并修正。现在三处一致 = 37。

> 这类缺陷不是"重复代码"，而是**两个数都看起来对**。

## 缺陷 3（P1 · 功能失效）文档承诺的 `--seed` 在已有库上必崩

### 现象

`python run.py --seed`（README 里写的"重建演示数据"）执行即崩：

```
sqlite3.IntegrityError: FOREIGN KEY constraint failed
  File "app/seed/seed_data.py", line 2694, in main
    clear_all(db)
```

**而全新的库第一次播种完全正常**——所以这个缺陷在第一次跑通时根本看不出来，
只有第二次执行才会暴露。

### 排查

清空逻辑原本靠一份手写的表清单：

```
库内实际表数：65
清空清单表数：58        ← 漏了 7 张
漏网：contract_payments / data_quality_issues / data_quality_reports /
      data_uploads / policy_matches / project_tasks / user_project_scopes
```

逐表删除定位到失败点：

```
✘ 删除 enterprises 失败：FOREIGN KEY constraint failed
   外键指向 parks（父表还有 4 行）
```

`policy_matches` 等表没有被清空，残留行指着 `enterprises`，把父表删除挡住了。

### 修复过程（两次失败才做对）

**第一次尝试**：改成由 ORM 自动推导删除顺序（`Base.metadata.sorted_tables`），
不再手工维护清单。→ 仍然失败，SQLAlchemy 给出警告：

```
SAWarning: Cannot correctly sort tables; there are unresolvable cycles
between tables "contracts, spaces" ...
```

`contracts` 与 `spaces` **互相引用**（循环外键），拓扑排序给不出可靠顺序。

**第二次尝试**：整库重置时临时关闭外键校验。踩了两个坑：

- `PRAGMA foreign_keys` **在事务内切换无效**，必须先 `commit()`；
- 它是**按连接生效**的，所以必须用会话正在用的那条底层连接执行，
  而且中途 `commit()` 会让连接代理失效（`AttributeError: 'NoneType' object has no attribute 'execute'`）。

**最终实现**：持有底层 sqlite3 连接，在同一条连接上完成"关外键 → 清空全部表 → 开外键"，
并在 `finally` 里确保约束被恢复（运行期不能少）。

### 为什么值得记一条

这是典型的**"文档承诺的入口是坏的"**：README 教用户重建数据，用户一执行就崩；
而开发者（包括 AI）每次都在全新库上验证，永远碰不到。
**"重启/重建"这类路径必须用"已存在数据"的状态去测。**

## 缺陷 4（P2 · 测试自身的坑）空断言让越权用例失效

写新增的越权用例时我这样写：

```python
st, d = call("GET", "/operation/work-orders?page_size=200", tenant)
if isinstance(d, dict) and d.get("items"):        # ← 问题在这
    foreign = [...]
    expect(not foreign, ...)
```

修完工单过滤后，`tenant1` 的工单列表变成**空**，`if` 不成立，
断言被整段跳过 —— 测试总数停在 49 项不变，**"修复"与"没测到"看起来一模一样**。

**修正**：断言无条件执行（空列表 → 无越界项 → 通过），另用 `record("INFO", ...)`
把每次的可见量打出来，便于人工判断"0 条"是正常还是异常。

> 教训：**带条件的断言等于没有断言。** 判断测试有没有真的跑，要看用例数变化，不能只看"没有 FAIL"。

## 缺陷 5（P2 · 体验问题）部分页面对"必然为空"的字段没做说明

`/contracts?expiring_days=90` 修正状态口径后，合同管理页的"90 天内到期"从 39 变为 37。
数值本身没问题，但与**用户前一天看到的数不一致**，且页面上没有任何口径说明，
使用者只会认为"数据出错了"。

**处理**：合同页的到期预警区块补上口径文案（"仅统计生效中/即将到期合同，已终止不计入"），
并在 `basis` 字段中同步。**数值变化必须给解释，否则会被当成新缺陷。**

## 附录 C：遗留问题（已确认，未在本次修复）

按"带 `enterprise_id` 的表"系统排查，仍有 6 张表在 API 层没有企业范围过滤：

| 表 | 影响 | 建议 |
|---|---|---|
| `energy_records` | 能耗按企业归属，但企业账号对能耗模块无权限（403），暂不可达 | 加过滤，与工单同批处理 |
| `approval_requests` | 审批单带企业归属，企业账号可见范围偏大 | 按企业过滤 |
| `parking_spaces` / `vehicles` | 车位与车辆属企业资产 | 按企业过滤 |
| `users` | 企业下属账号；企业账号无 `system` 权限，暂不可达 | 若将来放开企业侧账号管理，必须补 |
| `enterprise_contacts` / `enterprise_tags` | 企业子表，仅通过已加固的企业详情访问 | 低风险 |

**优先处理建议**：`approval_requests` 与 `energy_records`——两者都涉及企业经营信息，
且审批中心是企业账号能看到的菜单项。

## 附录 D：这次测试暴露的流程问题

1. **"本地全绿"不等于"环境可用"**：本次 5 个缺陷中，有 4 个在 92 项冒烟测试下完全隐形。
2. **多身份测试缺失**：平台有 15 个角色、9 级数据范围，但自动化测试只用过少数几个身份。
   建议把"每个数据范围至少一个身份 × 全部可见模块"纳入常规回归。
3. **手工维护的清单迟早会烂**：表清单、状态枚举、口径公式——凡是"手写一份"的地方，
   都应该改成从单一来源推导（本次已改掉两处：清空顺序、到期口径）。
